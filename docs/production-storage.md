# Little Feet production storage

Little Feet treats PostgreSQL and a private Cloudflare R2 bucket as one logical school-data system. PostgreSQL owns each file relationship and its authorization metadata. R2 stores only the binary object. The browser never receives R2 credentials or a permanent public bucket URL.

## Required configuration

Create a private R2 bucket and a bucket-scoped API token with Object Read & Write permission. Configure the four `CLOUDFLARE_R2_*` variables shown in `.env.example` on the server. Do not expose them through client JavaScript or commit their values. The application uses Cloudflare's S3-compatible endpoint with region `auto`.

The application readiness endpoint remains not-ready until PostgreSQL, durable sessions, encryption keys, an administrator, secure production cookies, and private object storage are configured. Live R2 connectivity still needs to be verified in the production environment.

## Supported ordinary files

One file is accepted per bounded request. PNG, JPEG, GIF, WebP, and PDF files are limited to 5 MiB. TXT and CSV files are limited to 2 MiB. Both the declared content type and decoded file signature/content are checked. Filenames are reduced to a safe leaf name; object keys are generated by the server under a hashed tenant prefix.

## Authorization and lifecycle

Private bytes are retrieved only through `/api/files/:id/content`. The route requires a Little Feet session, the same school ID, and access to the related learner, staff, school, post, or worksheet record. Object keys are never treated as authorization.

Upload is acknowledged only after the object and its database metadata are durable. Replacement creates the new object and relationship before retiring the old object. Deletion records a pending state before deleting bytes. Failures are returned to the caller and the metadata is restored or left in a recoverable lifecycle state.

## Backup and restore

1. Pause application writes or place the service in maintenance mode.
2. Record a common backup timestamp and the deployed application SHA.
3. Take a PostgreSQL backup that includes `little_feet_records`, `little_feet_metadata`, `little_feet_sessions`, and legacy `little_feet_app_state`.
4. Create an R2 inventory and copy/version the `schools/` object prefix to the approved backup location.
5. Store the database backup, object inventory, application SHA, and timestamp as one recovery set.
6. During restore, restore PostgreSQL first and R2 objects second while writes remain paused.
7. Run the authenticated file-integrity endpoint for every school. Resolve every missing object or size mismatch before reopening writes.

Database-only or bucket-only restores are incomplete. R2 lifecycle rules must not delete active Little Feet objects. Retention and legal deletion rules should be applied through Little Feet so metadata and bytes remain consistent.

## Isolated recovery rehearsal

`npm run recovery:rehearse` creates an encrypted coordinated recovery set in a separate private R2 bucket. It takes a repeatable PostgreSQL snapshot while holding short-lived shared locks, copies every active private object plus an R2 probe, restores the database into a generated isolated PostgreSQL schema, restores objects under an isolated recovery prefix, verifies row counts and object hashes, and removes the isolated restore targets. The encrypted recovery set and signed-by-hash manifest remain in the recovery bucket.

Required one-off environment settings are `LF_BACKUP_R2_BUCKET`, `LF_BACKUP_ENCRYPTION_KEY`, and `LF_RECOVERY_CONFIRM=PRODUCTION-ISOLATED-RESTORE`. The R2 credential must have read access to the live bucket and write access to the separate recovery bucket. Optional `LF_BACKUP_R2_ACCESS_KEY_ID` and `LF_BACKUP_R2_SECRET_ACCESS_KEY` allow a dedicated recovery credential. Do not add `LF_BACKUP_REHEARSAL_ID` to the web service until a real rehearsal has completed successfully.
